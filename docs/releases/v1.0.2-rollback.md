# EnthusiaLoreItems 1.0.2 — live SMP rollback

This plan is for a controlled upgrade of the currently installed Enthusia SMP LoreItems build to candidate `1.0.2`. **Do not assume the deployed binary is the published v1.0.1 asset:** earlier snapshots used distinct jar filenames and embedded versions. Obtain the remote JAR's actual SHA-256 and the current database/schema before any replacement.

## Prerequisite production evidence (not optional)

- Record exact installed JAR basename/size/SHA-256, embedded `plugin.yml` version, running Paper/Leaf and Java versions, deployed plugin/config hashes, current schema version and prior migration state.
- Record current instance/definition counts, pending deliveries, mutations, campaigns, recovery/review-required counts, anomalies, and tracking queue telemetry.
- During a scheduled maintenance stop, make and checksum a **complete** `plugins/EnthusiaLoreItems/` backup, including `loreitems.db`, any WAL/SHM sidecars, `config.yml`, `groups/` and all marker directories. Keep backups outside live plugin directories.
- Preserve an independently hashed copy of the original JAR and a manifest of the exact files. Check the backup by opening a separate database copy with `PRAGMA integrity_check` and `PRAGMA foreign_key_check`, and rehearse a restore using an isolated data directory.
- Verify exactly one active `EnthusiaLoreItems` plugin JAR will remain in `plugins/`. Never expose a temporary `.jar` alongside it that Paper could load.

## Prepare installation

1. Keep intake of new staff mutations/campaign starts paused during the maintenance window.
2. Stop the SMP cleanly. Wait for process exit and ensure writes and WAL checkpointing finish.
3. With the server stopped, compare remote checksum to the recorded prior baseline and candidate checksum to the immutable CI artifact.
4. Stage the new binary under a temporary **non-.jar** suffix, verify byte size and hash, then atomically promote it to the only active plugin JAR. Preserve the old binary outside the plugins loader path.
5. Start once and verify schema migration, SQLite integrity, service writable state, pending/review work, item identities, admin commands, and Geyser/Floodgate behavior before resuming operations.
6. Capture startup logs, queue telemetry and Spark profile for comparison with the historical baseline.

## Stop/rollback triggers

- SQLite integrity or foreign-key error, migration error, degraded/unavailable write state.
- Item loss, duplicate issuance, wrong-target removal, rejected accepted work disappearing, wrong identity binding, invalid durable replay, unexplained recovery/anomaly growth, or material new severe lag.

## Restore

1. Stop staff mutations and capture current logs/database state without overwriting the original backup.
2. Stop SMP cleanly. Preserve failed candidate directory and JAR separately for diagnosis.
3. Restore the **entire** pre-upgrade plugin data directory and the matching previously deployed original JAR. Confirm checksums. Do not install an older JAR over a potentially migrated database.
4. Restart in the controlled window, check writable service, SQLite integrity and foreign keys, item/tracking state, pending operations and marker consistency.
5. Account for physical copies or player actions that occurred after the backup: do not hide duplicate evidence by stripping item PDC data. Reconcile conflicting copies explicitly before returning staff write access.

Do not claim backup, restore rehearsal, production compatibility or Sentinel acceptance was completed until actual remote/test records exist. This document does not authorize a live mutation, restart or approval-gate bypass.
