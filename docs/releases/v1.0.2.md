# EnthusiaLoreItems 1.0.2 — release candidate

This version assigns a new, non-conflicting release identity to the merged tracking/performance work after the immutable published `v1.0.1` release. The `v1.0.1` tag and existing assets must not be replaced or retargeted.

## Runtime and compatibility

- Intended server: the single Enthusia SMP, Java 21, Paper/Leaf-compatible Minecraft 1.21.11.
- Durable storage: SQLite under `plugins/EnthusiaLoreItems/`; preserve all plugin files and marker directories.
- Public API and tracked item persistent-data identities are intended to retain their existing contracts.
- This release does not authorize server deployment or imply that current SMP database/schema, plugin dependency versions, startup or rollback have been directly verified.

## Changes since the published 1.0.1 release

- Reduce redundant item metadata reads in shulker/template tracking paths; preserve nested identity evidence, malformed and duplicate item handling.
- Batch destination inventory lookup for multiple tracked identities within the same movement event; preserve individual evidence.
- Coalesce routine periodic chunk reconciliation by world/chunk and publish backlog, source-specific completion/rejection and duration metrics.
- Prioritize event/lifecycle tracking requests over optional periodic scans in a full bounded queue, displacing only the youngest optional periodic entry, with three event scans per periodic opportunity.
- Skip nested `ItemMeta` access for ordinary non-shulker/non-bundle stacks while still validating tracked identity on every root item.
- Keep the unchanged total scan capacity, per-tick request budget and existing persistence/authorization paths.

## Production-admission conditions

1. Freeze a single exact source SHA and build `1.0.2` artifact; verify JAR SHA-256 and repeatable build.
2. Require all repo acceptance workflows, clean Gradle verify, changed-code Lizard, hosted Codacy zero new valid findings, and required independent reviews.
3. Resolve the independent Sentinel startup/toolchain failure and complete `PAPER_RESTART_OK` on the exact candidate, or document an explicitly authorized replacement acceptance process; never silently skip the check.
4. Identify the **actual** installed Bloom JAR hash/version, Java/Paper version, configuration, plugin dependencies, current SQLite `user_version`, pending destructive/recipient work, and write a pre-upgrade comparison record.
5. Before replacing any live JAR, stop the server cleanly, take an **offline and verified** full LoreItems directory backup including database, config, campaigns and markers, preserve the exact previous JAR, and record restore evidence. A live copy of only the main SQLite file is not a valid backup when WAL is active.
6. Verify clean startup, database integrity/read-write state, tracking, delivery, duplicate/anomaly audit, Floodgate identity and unchanged pending work during maintenance. Capture matched post-rollout Spark/MSPT and scan metrics.
7. Require the exact-JAR source-controlled approval marker to be approved only after actual evidence has been reviewed. The production release workflow must remain fail-closed until then.

## Non-goals and residual risk

A bounded number of scans per tick is not a strict wall-clock time limit. Event-only saturation can still reject new observations while preserving prior durable evidence. Historical Spark results are not a measurement of this candidate on production.

## Rollback

Follow `v1.0.2-rollback.md`. Restore the matched **pre-upgrade database and JAR together**, never only an older JAR over an unknown newer SQLite schema.
